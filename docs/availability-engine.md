# Availability engine

- **SQL fetches, TypeScript computes.** Postgres returns the raw rules and busy intervals for the requested window; a pure TypeScript function with no I/O does the interval math. The definition of done requires explaining why a slot did *not* appear, and a function can return a reason for every excluded time where a query returns only the survivors. Tests take constraints as arguments and need no database, so DST cases can number in the dozens and run in milliseconds. The public page reads through ordinary column-scoped grants; the all-SQL alternative would have needed a `SECURITY DEFINER` function, which runs as the owner and bypasses RLS. Wall-clock rules become instants only in TypeScript, so only one time-zone database (Node's) matters. Accepted cost: interval semantics exist in two places — the engine and the future exclusion constraint — and must agree exactly on endpoints. A test pins that agreement.
- **Temporal, native, no library.** Node 26 ships Temporal enabled by default; types come from the `lib` setting in `tsconfig.json`. Each kind of time has its own type — `PlainTime` for a wall-clock rule, `PlainDate` for a calendar date, `ZonedDateTime` for a rule placed on a date in a zone, `Instant` for an exact moment — so turning a rule into an instant cannot happen without naming a zone and choosing how to resolve DST gaps and overlaps. Rejected `@date-fns/tz` (the date-fns v4 successor to `date-fns-tz`): every value is a `Date` subclass, so the type system can't tell an instant from a wall time, and a forgotten `in: tz(...)` silently computes in the process's zone — Eastern on the dev machine, UTC in the container. Accepted costs: a newer API with thinner documentation; `pg` returns `timestamptz` as a `Date`, converted at the database boundary; no Temporal polyfill anywhere in the dependency tree, since a polyfill alongside the native global produces objects with different prototypes. The browser does not need Temporal: the API returns instants and the frontend formats them with `Intl.DateTimeFormat`, which matters because stable Safari does not ship Temporal as of September 2026.
- **The current time is an argument.** The engine never reads the clock. Minimum booking notice needs "now", and a function that fetches it itself is neither pure nor testable at, say, 23:30 in Vienna the night before the clocks change.
- **Intervals are half-open, `[start, end)`.** Start included, end excluded — Postgres's range default — so back-to-back appointments touch without overlapping. The engine sets this rule; the exclusion constraint is written to match it.
- **Weekdays are ISO: 1 = Monday, 7 = Sunday.** Matches Temporal's `dayOfWeek` and Postgres `ISODOW`. JavaScript's `getDay()` returns 0 for Sunday; convert wherever the browser builds these values.
- **Wall-clock rules: end after start, or end `00:00` meaning end of day.** `00:00–00:00` is invalid. Enforced by `CHECK` on `business_hours` and `staff_working_hours`. Overnight hours are two rows split at midnight; the engine merges touching intervals so a service can cross midnight. An end of `00:00` expands to the *start of the next day* in the tenant's zone, not to "00:00 on the next date" — some zones change clocks at midnight, where 00:00 doesn't exist.
- **Split shifts are multiple rows** per weekday.
- **The time zone lives only on `tenant`.** No zone column on rule tables; one source of truth.
- **Time off is stored as instants** (`timestamptz`), not local dates. "Off all of 30 October" is converted to the tenant's local midnight-to-midnight when the owner enters it, in the owner UI. Accepted cost: if a tenant's zone ever changes, existing time off does not move with it.
- **Staff-owned rows carry `tenant_id` for RLS, pinned by a composite foreign key.** `(tenant_id, staff_id)` references `staff(tenant_id, id)`, so a row can't name one tenant and another tenant's staff member.
- **Slot starts on a 15-minute grid aligned to local quarter hours.** Candidate start times are :00, :15, :30 and :45 on the salon's wall clock, regardless of when it opens — a salon opening at 09:10 offers 09:15 first. Chosen for legibility: customers read and remember quarter hours. Accepted cost: the grid strands gaps (a 45-minute cut ending at 10:45 can leave a 15-minute sliver no service fits), which makes the parked gap-filling feature a scoring problem over the grid rather than a structural one.
- **Grid times on DST-transition nights.** Only reachable with overnight hours. On fall-back night one local hour occurs twice — 02:00–02:59 in the EU, 01:00–01:59 in the US — and only the first occurrence (the earlier instant, still on summer time) is offered, so every displayed time is unique; the second occurrence's hour is lost once a year. On spring-forward night the missing hour's grid times (02:00–02:45 in both regions) are skipped, not shifted: Temporal's default `'compatible'` disambiguation would move 02:15 to 03:15, duplicating the real 03:15 slot, so the engine must detect nonexistent local times rather than let the default resolve them. Services and buffers are measured in real elapsed time on instants, so a 60-minute service across the repeated hour still takes 60 minutes.
- **Buffers add.** An after-buffer of 10 minutes on one appointment and a before-buffer of 5 on the next require 15 minutes between them. Each appointment blocks `[start − before-buffer, end + after-buffer)`; two blocked intervals may touch but not overlap, so the exclusion constraint on blocked intervals enforces the additive rule by itself. `appointment` therefore stores both the service times the customer sees and the blocked interval.
- **Buffers only collide with other appointments.** Working hours, business hours and time off constrain the service interval alone; buffers may extend past all three. A 09:00 service with a 10-minute before-buffer is bookable for a stylist who starts at 09:00, and a service ending 12:55 with a 10-minute after-buffer is bookable when time off starts at 13:00 — time off only matters once the stylist's work is done. Buffers still may not overlap another appointment's blocked interval.
- **Requested dates are the salon's calendar dates, and times are shown in the salon's zone.** "25 October" means the 25th in the tenant's zone, and every time on the booking page is on the salon's clock, labelled with its zone. The customer will be physically in the salon, so its local time is the one that matters, and date headings and the times under them never disagree. Supersedes "rendered in the viewer's timezone" in the scope doc.
- **Resources are blocked for the buffers too.** A wash station is unavailable for the appointment's whole blocked interval, `[start − before-buffer, end + after-buffer)`, because it needs preparing and cleaning. Staff and resource conflicts therefore use the same blocked interval, and both exclusion constraints can be written on one column.
- **Overlapping hours rows are unioned.** Two overlapping `business_hours` or `staff_working_hours` rows for the same weekday are merged by the engine, not rejected by the database. The owner UI may save them.

## Engine internals and request handling — decided 10 October 2026

- **Rule boundaries resolve toward the longest real trading day: `'compatible'` for a start, `'later'` for an end.** A wall-clock boundary can be nonexistent or ambiguous on the two clock-change nights, and this is not exotic — an overnight business is stored as `18:00–00:00` plus `00:00–02:00`, and in a zone that shifts at 02:00 local a closing time of `02:00` is hit by both transitions every year. `PlainDate.toZonedDateTime` accepts no options and always behaves as `'compatible'`, so choosing requires the `PlainDateTime` route: `date.toPlainDateTime(rule.startTime).toZonedDateTime(timeZone, { disambiguation })`. For a start, `'compatible'` pushes a nonexistent time forward (spring) and takes the first of a repeated pair (autumn) — the earliest real opportunity to open. For an end, `'later'` pushes forward identically in spring but takes the second of the repeated pair in autumn, so a bar open until 02:00 gets the extra hour it actually trades. Both boundaries therefore resolve toward maximum real trading time, which is also how the asymmetry is defended: a start resolves to the earliest valid moment, an end to the latest. Rejected `'reject'`, which turns one ordinary hours row into a failed request once a year, and rejected catching the `RangeError` to mark the day closed, which breaks a whole day over data that was never wrong.
- **A slot belongs to the calendar date it starts on.** A 90-minute service starting 23:30 on the 25th ends at 01:00 on the 26th and appears only under the 25th; times after midnight from the same continuous open period appear under the 26th. Rejected filing both dates, which double-counts one instant under two headings. Rejected the business-day grouping a bar owner would use ("Friday night" running to 2am Saturday), because it contradicts the settled rule that requested dates are the salon's calendar dates — under it, asking for the 26th returns times filed under the 25th. The decisive argument is that this direction is recoverable and the other is not: an owner calendar can group start-keyed slots back into sessions, since it has the instants and can see which came from one stretch, whereas a customer view cannot undo business-day filing without re-deriving dates, which is the engine's job. Accepted cost: a single-day view shows 23:30 as the last slot and not 00:30, so a day view must request two days and label the second day's early hours.
- **`noQualifiedStaff` stays a boolean.** It does not distinguish "nobody here is linked to this service" from "the requested stylist is not linked to it", because the engine's input contains no `preferredStaffId` and distinguishing them would mean adding a field that affects no computation purely so the engine can echo it back as a label. The controller read the query string and already knows. Read the flag as "none of the candidates you asked about are qualified". The genuinely useful answer in the second case — who *does* offer this service — needs a second query with the preferred filter dropped, and is parked.
- **Staff reasons take precedence over resource reasons.** `ExcludedTime.reason` holds either one tenant-wide fact or the complete set of per-staff facts, never both, so a time where every stylist is busy and every resource is taken must report one. It reports the staff reasons, because in that situation both are usually the same appointments seen from two angles — the stylists are busy doing appointments, and those appointments hold the resources — so the staff reasons name the cause and the resource conflict names the consequence. The resource reason is not suppressed in general: when a stylist is free and only the resource is held, no staff reason exists and `'noAvailableResource'` is reported as the sole cause. Consequence for the implementation: the resource check runs only when the staff check left survivors. Accepted cost: an owner wondering whether to buy a third wash station is better served by the resource reason, and that belongs in a capacity view with its own query rather than a different precedence here.
- **The requested range is capped at 31 days, in the controller.** A month view is the largest range a real booking UI asks for. The cap and the `throughDate >= fromDate` check live in the controller, not the engine: an over-long range is a bad request, and the engine would have to either throw — awkward for a pure function tested by its return value — or silently truncate, which would leave the response's days disagreeing with the range the frontend used to draw its calendar.
- **A `fromDate` in the past is accepted, and minimum notice handles it.** Past days come back `open` with every time excluded as `'tooSoon'`, which is true and needs no new code, since the notice check already excludes everything before `now + minimumNotice`. Rejected returning a 400, which forces every client to compute `max(today, monthStart)` before asking and lets each one get it wrong differently. Rejected clamping `fromDate` server-side, which would make the returned days disagree with the requested range. Accepted cost: a large `excluded` payload for days nobody can book.
- **Request-shape validation lives in the controller.** `fromDate` and `throughDate` are parsed with `Temporal.PlainDate.from` in a try/catch and rejected with a 400 there, alongside the range cap and the ordering check, so every request-shape rule sits in one function. Previously a malformed date reached the mapper and surfaced as a 500, which blames the server for a client error. `AvailabilityQuery` keeps holding strings, because the fetch layer passes them straight to `computeQueryWindow`; the mapper parses them a second time, and parsing a date string twice is cheaper than pushing Temporal values into the services layer's public type.
- **The public endpoint returns `status` and `slots` only; the full result is owner-side.** `BusyInterval` carries an `appointmentId` and exact times, so the reasons are a readable map of the salon's whole booking schedule per stylist — a leak on a public page even without customer names. Coarse reasons do not fix it: a greyed-out time labelled `'busy'` with no payload still maps the day. Only `'tooSoon'` and `'doesNotFitBeforeClosing'` are safe to expose, and the frontend can derive both from the notice and the closing time. Accepted cost, and the real one: the "explain why a slot did not appear" demonstration cannot live on the public booking page. It lives on the owner calendar, which is where that explanation is useful anyway.
- **`contains` is its own function, and it depends on the merge.** `evaluateGridTime` needs containment three times, and deriving it from `intersect` allocates a result object and compares two instants at every call site. The non-obvious part: checking a service against a stylist's shifts with `.some(period => contains(period, service))` is equivalent to "inside the union of their shifts" **only because `mergeTouching` has already glued touching periods**. On unmerged periods, a service spanning two adjacent shifts would be inside the union but inside neither period and would be wrongly rejected. The merge is correctness, not tidiness.
- **Engine-internal types stay in `engine.ts`.** `types.ts` is the contract — the shapes that cross the boundary between `src/services/` and `src/availability/`. Intermediate shapes the engine builds for itself (`StaffDaySchedule`, `GridTimeContext`) are exported from `engine.ts` so tests can build fixtures, but are not promoted into `types.ts`, where they would read as part of the contract and make it impossible to tell which types a caller needs. Keeping them private also leaves their representation free to change — pre-sorting busy intervals, say — without that reading as a contract change.
