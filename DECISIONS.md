# Whiteboard — settled decisions

Why the project is built the way it is. Closed unless something in the build
proves them wrong; reopen date October 1, 2026.

Infrastructure and deploy decisions live in [`docs/deployment.md`](docs/deployment.md).
The database role model is in [`docs/database-roles.md`](docs/database-roles.md).

## Product

- **Domain: salon / independent service business booking.** Chosen over restaurant reservations, which is a different algorithm — table-fitting rather than constraint intersection — and over systems projects (Raft, a workflow engine, a storage engine), which have a higher ceiling but a worse fit for a bounded build.
- **Positioning: sold as salon software, built as a general engine.** The data model contains no salon-specific concepts — `staff`, `service`, `resource`, `appointment`. The same schema serves a tattoo studio, a physio clinic, or a dog groomer unmodified. Salon vocabulary lives in UI copy and seed data only. No label-customization feature: generic names in code, salon words in copy.
- **Positioning amended 4 Nov 2026: sold to service-based organizations, not salons.** Salon wording in code, copy, tests and docs is now "organization". The schema was already domain-neutral, so nothing structural changed. Kept: the origin story (it was a salon), the demo tenants' names, and migration comments, which are history. Accepted cost: "organization" also names Better Auth's `organization` table, so in comments it can mean either.
- **Model rule:** a concept enters the schema only if it exists in at least three candidate verticals. Staff qualifications, service durations, buffers, and room constraints qualify. Walk-in queues, product retail, and chair rental do not.
- **Not a commercial product.** This is a portfolio artifact. The market has capable free incumbents, and a live customer would mean production obligations the project isn't structured to meet.

## Stack

- **TypeScript / Node / Express.**
- **Node 26.** Node 20 reached end of life on 30 April 2026 and receives no security patches — a non-starter for a process that parses untrusted input from the public internet. Node 24 is the Active LTS today but moves to Maintenance on 20 October 2026; Node 26 becomes Active LTS on 28 October and runs to April 2029. It also matches the local dev version and `@types/node`, which removes a class of bug where code typechecks against APIs the runtime doesn't have. Accepted tradeoff: less ecosystem soak time than an established LTS line. Pinned in the Dockerfile, the CI workflow, and `engines`.
- **Separate API + Vite/React frontend, not Next.js.** The REST API with webhooks is a first-class deliverable, and reminder emails need a long-running scheduler rather than a request-scoped one.
- **Express over NestJS.** Multi-tenancy, timezone-correct scheduling, and database-level constraints are enough new concepts without a framework to learn alongside them.
- **PostgreSQL 18**, with `node-pg-migrate`. **Migrations are the schema; the database is their output.** `node-pg-migrate` lives in `dependencies`, not `devDependencies` — the production container executes it as a one-shot migrate service, so it is a runtime dependency regardless of feeling like tooling.
- **Compiled with `tsc`, not run through `tsx` in production.** `tsx` transpiles without typechecking, so for a while nothing had ever checked this codebase. Two configs: `tsconfig.json` builds `src/` to `dist/`; `tsconfig.check.json` extends it with `noEmit`, a root of `.`, and a wider `include` covering tests, scripts, and config. `build` compiles what ships; `typecheck` checks what should be correct. CI runs both.
- **Scheduler runs in-process, not as an external cron.** A long-running instance removes the constraint that pushed reminder emails toward a scheduled CI job, which was the original argument for a separate API in the first place.

## Architecture

- **Availability is computed, never stored.** Bookable times are derived per request by intersecting business hours, staff working hours, approved time off, existing appointments plus buffers, and resource conflicts. No pre-generated slot rows. See [`docs/availability.md`](docs/availability-engine.md) for the algorithm.
- **Invariants live in the database, not application code.** Booking races are prevented by a Postgres exclusion constraint on `(staff_id =, during &&)` via `btree_gist`, so the check and the write are one atomic operation. Check-then-insert has a race window; this does not.
- **Tenant isolation is enforced below the query layer**, by row-level security with a session variable — not by a `WHERE tenant_id = ?` a developer can forget. A test proves cross-tenant reads fail.
- **One database role per access path, none of them the owner.** `whiteboard_app`, `whiteboard_signup`, `whiteboard_public`, `whiteboard_auth` — each scoped to what it needs, none bypassing RLS. Better Auth originally ran on an inline pool as the owner role, which meant password hashes and session validation bypassed RLS on every table in the database; it now has its own role scoped to seven tables and no domain access. In November 2026 `whiteboard_app` was narrowed the same way: it had every privilege on every table, Better Auth's included, and now holds per-table grants matching what the code does, with no default privileges for future tables. See [`docs/database-roles.md`](docs/database-roles.md).
- **Migrations must not hardcode a database or role name.** `current_database()` and `current_user` via `format()`. Both bugs were found by CI running against a fresh cluster, and both would have run clean in production and stayed latent.
- **Sign-up provisions across two connections, so it can't be one transaction.** The organization and its owner membership are created through Better Auth; the tenant row through the sign-up role, with the organization link set in the insert itself so a tenant can never exist unlinked. A retry resumes from whatever the last attempt left, and every branch decides from what is in the database rather than from an error code, which also covers two sign-ups racing for one address. "Address taken" only ever means another account holds it.
- **Deleting staff, a service or a resource archives it.** Appointments reference all three and past ones are history, so the row gets `archived_at` and drops out of setup, booking and availability. A delete is refused while future bookings depend on the row, and a resource can't be removed while it is the only one a service can use, because a service with no linked resource needs none. A booking racing an archive loses: the archive locks the row, the booking's foreign key waits on that lock, and the booking re-checks after its insert.
- **Three signed-in roles: owner, manager, staff.** They map onto Better Auth's `owner`, `admin` and `member`. A manager is an owner minus people: setup, the calendar and inviting staff, but only an owner invites managers or removes anyone. Better Auth's default `admin` can invite admins and change roles, so the manager role is defined with no member permissions and a `beforeCreateInvitation` hook refuses a manager invite from anyone but an owner. Both are enforced in Better Auth itself, so calling its routes directly gets the same answer as the app's.
- **An organization can have several owners, and an open one always has at least one.** Owners change anyone's role, their own included. Better Auth only stops the last owner demoting themselves, by counting and then updating, so two owners demoting each other at once could both pass. A trigger on `member` refuses any role change or removal that would leave an open organization without an owner; it takes the organization's row `FOR UPDATE` first, so changes to one organization's owners run one at a time, and its count, a new statement under READ COMMITTED, sees what the previous one committed. A test races two transactions and fails without the lock. Closed organizations are exempt, so their last owner can still delete their account. It relies on READ COMMITTED; under REPEATABLE READ the count would read an old snapshot.
- **Staff see only their own appointments, enforced by RLS.** For `whiteboard_app`, an appointment is visible when the caller manages the tenant or it belongs to the caller's own staff row, and a customer only through one of those appointments. Both are worked out in the database from `app.user_id`, so a route that forgets to filter still can't leak another staff member's customers, and a call with no user set sees nothing. Staff can change their own working hours and nothing else. Archiving a staff row ends what its login can see.
- **Staff get logins by emailed invitation, sent through Amazon SES.** The invitation records which staff row it is for, and accepting links the row to the login. Like sign-up it spans Better Auth's connection and the app's, so it decides from the invitation's state and the membership in the database and is safe to retry. SES because the instance profile can send with no API key to store; the cost is the sandbox, which only delivers to verified addresses until AWS approves production access.
- **Password reset and email verification exist; verification is never required.** A reset emails a one-hour, one-use link straight to `/signin/reset`, which posts the token, and using it ends every session. Asking for a reset answers the same whether or not the address has an account. Verification goes out at sign-up and on request, but nothing waits for it: while SES is in its sandbox most of these can't be delivered, and requiring them would stop every real sign-up. Once production access arrives, requiring it is a one-line change worth reconsidering. Neither email can fail its request; a failed send is logged. With verification in place, a confirmed user's email change waits for a link to the new address, while an unconfirmed one still applies at once behind the password check.
- **Customer emails never undo a booking.** Each is sent after the change commits; a failed or unconfigured send is logged and the response says `emailed: false` so the page keeps showing the manage link. The confirmation is the only place the manage token goes besides the booking response, since only its hash is stored. Later notices point back to that email instead.
- **Closing an organization archives it, with 30 days to reopen.** An owner closes it; every future booking is cancelled and its customer emailed, and the organization disappears from every lookup, so its page, its members' access and its calendar go at once. Nothing is deleted. For 30 days the owner can reopen it from their account page (cancelled bookings stay cancelled) and the slug stays taken, so a mistaken close loses nothing and the address can't be grabbed while customers still have it bookmarked. After 30 days the slug is released lazily: the next sign-up that asks for it calls `release_closed_slug`, which renames the closed organization to `<slug>--closed-<id>`, a form no one can pick. No scheduled job is needed. An old manage link is checked first against `closed_organization_for_token`, across tenants, so it still says the organization closed permanently even after someone new owns the address. Both functions are `SECURITY DEFINER`, each does one narrow thing, and each is granted to the one role that needs it. Closing takes the tenant row FOR UPDATE, which a booking's foreign key has to wait for, and booking re-checks the tenant after its insert, the same pattern as archiving staff.
- **People can delete their own account, but not as the last owner of an open organization.** An open organization with no owner couldn't be run or closed, so the last owner closes it or makes someone else an owner first. Deleting removes the sign-in, sessions and memberships, and any invitations the person sent (their foreign keys cascade); a staff row they were linked to stays, unlinked, so its history and bookings are kept. Better Auth would let a session less than a day old delete without a password; a `before` hook always requires one, so a stolen cookie isn't enough. Changing your email asks for it too: until verification exists, Better Auth applies an email change at once, and a stolen cookie that could move the address could then reset the password. Changing the password signs out every other session, since a suspected leak is the usual reason to change it.
- **Time off is entered as wall clock and stored as instants.** "Dec 24 to 26" or "Friday 9:00 to 12:00" in the organization's zone, converted on the server so the browser's zone never matters. No time means the whole day, from that day's start to the next day's, which is 23 or 25 hours across a clock change. DST edges resolve like working hours, toward the longer absence: an extra blocked hour costs a booking, a missing one books someone who isn't there. Staff ask for time off and owners or managers approve or decline it; time off an owner or manager adds is approved at once. Only approved time off blocks availability, because a request that blocked on its own would let anyone freeze their calendar; the cost is that bookings can land in a window while it waits, and approving says how many. Staff read only their own rows, because the reason is private, and may withdraw a request until it's approved. RLS enforces all of it, including that staff can only insert pending rows and never change a status, so the routes carry no role checks. Approve and decline move only a pending row, in the UPDATE itself, so two managers deciding at once can't both win. Adding time off over booked appointments leaves them booked and says how many, since moving someone's appointment is a person's call.
- **Owners book through the same rules as customers.** Owner bookings and moves from the calendar pass the same offered-slot check and exclusion constraints as the public page, so an owner can't book a time the engine refuses. The calendar's "why isn't this time bookable" comes straight from the engine's per-staff reasons, which the public endpoint strips.
- **Public routes are rate-limited per IP, in memory.** Booking emails whatever address it is given, so unlimited it is a way to send mail with our domain; reads run the engine. Bookings, token routes and reads each get their own allowance, so one can't use up another. The counts live in the one Express process; a second instance would need a shared store, and a deploy resets them, which only errs toward allowing. Per IP means people behind one office NAT share an allowance, which the limits are loose enough to absorb. Express trusts exactly one proxy hop, Caddy, which replaces any client-sent `X-Forwarded-For`; without that every request looked like Caddy and shared one bucket.
- **UUID primary keys** (`gen_random_uuid()` via pgcrypto). Sequential ids are enumerable, and appointment ids go in emailed links.
- **Time:** wall-clock rules (business hours, working hours) stored as local time plus an IANA zone id on the tenant. Appointment instants as `timestamptz`. Never a fixed offset like `+01:00` — offsets don't survive DST, and tenants in different regions don't shift on the same dates.
- **Schema hedges that cost nothing now:** a capacity column defaulting to 1, and staff nullable on appointment. Keeps group classes and resource-only booking possible later without a painful migration.

## Scope

**In:** tenant provisioning · staff, service, and resource management · working hours and time off · availability engine · public booking page per tenant · book, cancel, reschedule · staff and owner calendars · email notifications · appointment audit trail · REST API with webhooks.

**Out unless done with core:** payments and deposits · recurring series · group bookings · waitlists · calendar sync · SMS · packages and loyalty · custom intake forms · reporting dashboards · walk-in queues · product retail · mobile apps · custom domains · label customization.

Several of those are how a commercial version would make money. None of them matter if availability is wrong.

**Parked until the core is done:** intelligent gap-filling — cancelled slots offered to waiting customers first-come-first-served, and slot scoring that prefers times packing the day tightly over ones stranding unusable gaps. Cheap on top of the existing engine, and it's the receptionist judgment the project's thesis is built on.

## Phases

| Phase | Gate |
| --- | --- |
| Tenancy, auth, roles, core model, **deployed** | Two tenants live at a URL; a test proves neither can read the other |
| Availability engine | Correct slots from hours, time off, buffers, bookings, and resources — including across a DST boundary |
| Booking flow, public page, concurrency | Two simultaneous requests for one slot; exactly one wins |
| Calendars, reschedule, cancel, notifications, audit | A staff member sees their week; a customer reschedules from an email link |
| Hardening: seed data, API docs, demo tenants | A stranger books an appointment from the URL with no instructions |

**Deployed in phase one, not at the end.** An empty app was live at a real address over TLS, with an automated pipeline, before it did anything interesting.

## Definition of done

Sign up as a new organization. Add two staff members with awkward hours and one wash station. Define a service that needs the station and one that doesn't. Open the public page and book both.

Then explain why a particular time slot did not appear.

Met on production on 6 November 2026: self-serve sign-up, owner setup, and the owner calendar, whose "why isn't this time bookable" answers the last line.

Staff accounts and managers were added afterwards, on 6 November, at the cost of the week's slack, followed by the customer's confirmation, cancellation and move emails. Reminders are left out: they need something that wakes up on a schedule, which nothing in the app does yet.
